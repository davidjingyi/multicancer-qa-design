# 多癌种LLM问答设计思路

## 设计主张：让大模型成为主导者

核心方向是摆脱以向量化、Embedding、Chunk 和向量数据库为中心的传统 RAG 流水线，转而发挥大模型的语言理解、上下文判断和综合表达能力。大模型不再只是检索结果出来后的语言润色器，而是问答过程中的核心参与者：理解用户问题、在未预设时判断癌种、结合对话上下文，并依据指南证据组织回答。

指南仍是医学回答的事实依据。PDF 按癌种隔离，程序负责限定检索边界、检查证据是否足够，并返回原文文件和页码。这里强调的是抛弃传统向量 RAG 作为系统核心，而不是丢弃指南证据和来源追溯。

**当前实现边界：**癌种自动判断和答案生成由大模型完成；PDF 页的初筛与排序仍由本地全文关键词算法负责。也就是说，大模型已从“事后润色”进入问题理解和回答核心，但尚未接管检索器的每一步决策。

网站入口：<https://oncompass.site/>

## 一轮问答的处理流程

1. **读取癌种设置。** 用户可以在页面预设癌种。预设后，服务使用该癌种目录，不调用癌种分类模型。
2. **自动判断（仅在未预设时）。** 服务把本轮最新问题发送给大语言模型，由模型从服务端癌种白名单中选择 `cancer_id` 并返回置信度；信息不足、非肿瘤指南问题或多癌种主次不明时进入澄清流程。当前置信度门槛为 0.55；结果不可靠时要求用户补充或预设癌种，不继续检索。
3. **检查癌种冲突。** 如果问题明确提到与所选范围不同的癌种，服务会要求用户切换癌种或拆分问题，避免混用指南。
4. **限定目录检索 PDF。** 检索器只遍历癌种映射所指向的目录，不跨癌种搜索。每页正文按问题中的中文词组和英文/数字词项匹配并排序，最多选取 8 个相关页；同一 PDF 最多取 3 页。该检索使用全文关键词评分，不依赖向量数据库、Embedding 或人工切块。
5. **提取 PDF 正文。** 可直接读取的数字 PDF 使用 `pdftotext`。正文较少的扫描页会通过 `pdftoppm` 转成图像，再由 Tesseract 中文/英文 OCR 识别。
6. **维护文字缓存。** 缓存按癌种和 PDF 路径隔离，并记录 PDF 的 SHA-256。检索时发现 PDF 内容变化会重新提取；PDF 被删除时，相应缓存会清理。
7. **生成回答并返回来源。** 只有检索到足够证据才调用回答模型。回答附 PDF 文件名、目录和页码；没有证据时直接说明未检索到足够材料，不生成医学结论。

## 模型调用次数

- **用户预设癌种：**跳过分类调用；检索到证据后调用一次回答模型。
- **自动判断癌种：**先调用一次分类模型；分类通过且检索到证据后，再调用一次回答模型。
- **分类不确定、癌种冲突或未检索到足够证据：**不会继续调用回答模型。

所以自动判断并成功回答时通常是两次模型 API 调用；预设癌种并成功回答时通常是一次。PDF 文本提取与关键词检索在服务端本地进行，不额外调用模型。

## 对话上下文和接口

聊天页面按登录账号及癌种保存浏览器本地的历史记录；发送时只附带有限数量的最近消息，并过滤明显属于其他癌种的上下文。历史记录删除会移除当前浏览器中保存的该条对话。

服务提供 OpenAI Chat Completions 风格接口：

```text
POST https://oncompass.site/v1/chat/completions
Authorization: Bearer <登录令牌或 API Key>
Content-Type: application/json
```

请求可以使用标准 `model`、`messages`、`stream` 字段，并通过 `cancer_id` 预设癌种。响应符合 `choices[0].message.content` 的常见格式，并增加癌种判断结果、检索状态和 `sources` 来源信息。当前仅支持 `stream: false`。调用接口也需要有效身份认证。

## 使用边界

该系统用于健康教育和就医沟通，不替代医生诊断或治疗建议。回答是否可靠取决于目录映射、PDF 版本与可读取正文；使用者应核对页面展示的原文来源。内测网站不应上传或公开账号密码、模型密钥、患者资料及受版权限制的指南 PDF。
