# 多癌种LLM问答设计思路

我不想再围着向量化和向量数据库，按照程序员时代思路，做一种低效检索的方式，也就是所谓的传统 RAG。这种方式本质上是把LLM当作了文字润滑器来使用，LLM本身不需要检索和理解信息，只需要挑选出符合用户问题的相关内容，拼凑成一段看起来有逻辑的文字输出。在LLM发展到今天，这种方式甚至不如直接裸用LLM来问答。

在医学领域，尤其是肿瘤领域，指南仍然是兼具了严谨度和前沿性的文件。LLM的训练和发布速度永远跟不上医学的实际进展。一种外挂知识库的思路给LLM来辅助回答，仍然是必要的。

基于现在的LLM普遍支持多模态的输入，以及到达1M的上下文长度，一种思路是可以考虑的：用于的问题先路由出特定的癌种，再路由到特定的几份前沿指南，这些文件作为附件，随着用户的问题一并传输给LLM。就如同全世界很多患者正在做的事情：自己去下载了指南，然后发给LLM让LLM来通俗易懂地解读，然后再获取到建议。我只是把用户目前手动做的事情前置做了一遍。

网站入口：<https://oncompass.site/>

如果用户已经选了癌种，就按这个选择去对应文件夹找 PDF。如果没选，先让大模型从服务器已有的癌种列表里判断，并给出置信度。现在的门槛是 0.55；几种癌症分不出主次，就先请用户补充，不往下查。问题里提到的癌种和当前选择对不上时，也会请用户切换癌种或把问题拆开，避免拿错指南。

癌种确认后，只搜对应文件夹，里面是特定癌种的几个权威指南文件，包括NCCN、CSCO、ESMO等国际主流的肿瘤研究组织。

网页之外，也提供 OpenAI Chat Completions 风格的接口：

```text
POST https://oncompass.site/v1/chat/completions
Authorization: Bearer <登录令牌或 API Key>
Content-Type: application/json
```

请求用常见的 `model`、`messages`、`stream` 字段，也可以通过 `cancer_id` 预设癌种。回答放在 `choices[0].message.content` 里，同时会返回癌种判断、检索状态和 `sources` 来源。目前支持 `stream: false`，调用接口需要有效身份认证。

## 使用边界

这个问答工具用于健康教育和就医沟通，不能替代医生诊断或治疗建议。回答是否可靠，和癌种目录对应得是否正确、PDF 是否为合适版本、正文能否正常读取都有关系；看到回答后，仍应核对它引用的指南原文。账号密码、模型密钥、患者资料和受版权限制的指南 PDF 不应公开。
